# 连续测试先高分后归零：截图坐标错位修复

日期：2026-10-12。本轮处理公共截图链路，不针对某个脚本、图标或游戏增加特判，不降低匹配阈值，不修改已保存的模板、条件或路线。

## 实际复现与原因

在本机 MuMu / Android 12 / 900×1600 竖屏中，使用已有“测试功能”场景的 Play 商店图片条件，允许差异 20%（接受阈值 80%），复现持续显示 0%。隐藏检测高亮框后仍然失败，排除红框干扰。

临时抓取实际送入识别器的帧后确认：场景检测精度 936，缩放比例 0.585，预期帧尺寸 527×936。实际帧虽然是这个尺寸，却包含原始屏幕左上角的裁剪，图标仍处于原始像素位置，并没有随整个屏幕缩小。模板和搜索区域已按比例缩放，因此无法在相应位置找到目标。开始时高分、随后归零与全尺寸帧向错误缩放帧切换相符；本轮直接复现并确认的是错误裁剪和持续漏检。

这是采集几何错误，不是测试界面把正常结果清零，也不是防重复手势保护阻止识别。上一轮像素通道与匹配算法的测试没有覆盖设备实际的虚拟显示缩放行为，所以没有发现这项兼容性问题。Android 文档也区分了投影、虚拟显示和输出 Surface，缩放行为需要考虑设备实现及系统版本：[Media projection](https://developer.android.com/media/grow/media-projection)。

## 修复与影响范围

- `DisplayRecorder.kt`：始终以当前物理屏幕大小采集，只在真实屏幕尺寸变化时调整虚拟显示。修改识别精度时不再缩小系统投影，而是调整应用内的识别帧大小；旋转时先脱开旧 Surface，再调整物理采集尺寸和重新连接。拒绝尺寸不符合当前采集配置的旧帧。
- `DetectionFrameScaler.kt`：从完整截图显式缩放到检测尺寸，最多复用一个输出 Bitmap 和 Canvas，不逐帧创建大图，不保存截图历史；透明像素覆盖旧帧，防止残留目标。
- `DetectorEngine.kt`：更新调用注释，保留既有启动、取消、旋转和路线动作的处理顺序。
- `DisplayRecorderTests.kt`、`DetectionFrameScalerTests.kt`：新增 10 项回归，覆盖精度切换不调整采集尺寸、真实旋转、完整画面右下角目标、横竖屏、连续换帧、透明像素清除、缓冲复用、尺寸校验、原图保留与新帧语义。

颜色、文字、数值与图片共用这个入口。前三类仍按照既有策略保留原始像素，不额外缩小；图片条件仍使用原来的检测精度和缩放坐标。截图、框选、路线坐标继续使用物理像素。不新增依赖、权限、模型或数据库迁移。

代价：只含图片的低精度场景也先读取完整画面，额外保留一个缩小的检测缓冲。本次 900×1600 → 527×936 的 ARGB 缓冲分别约 5.76 MB 与 1.97 MB（不含系统 Surface/原生缓存）。应在低内存手机继续观察长期内存与帧率，不能把短测等同于两天稳定性验证。
